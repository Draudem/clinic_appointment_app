# Телефония: Asterisk → AudioSocket → серверный STT

Инструкция для того, кто разворачивает Asterisk. Серверная часть уже готова
и проверена: принимает поток аудио по протоколу AudioSocket, распознаёт речь
на сервере (GigaAM, русский) и отдаёт текст по HTTP.

---

## 1. Что нужно знать заранее

| | |
|---|---|
| **Адрес сервера** | `10.2.171.217`. **Уточнить перед тестом:** адрес выдаётся по DHCP и меняется при перезагрузке — `hostname -I` на машине с бэкендом |
| **Порт AudioSocket** | `8091` — сюда подключается Asterisk, **не** на порт HTTP |
| **Порт HTTP (спросить текст)** | **`8090` в Docker**, **`8080` при локальном запуске** через `./gradlew bootRun` |
| **Формат аудио** | PCM 16 bit, **8 кГц**, моно, little-endian — это фиксировано самим Asterisk |
| **Авторизация** | `/api/stt/*` закрыт JWT: сначала `POST /api/auth/login`, потом заголовок `Authorization: Bearer <token>` |

> **Почему два HTTP-порта.** В `application.yml` дефолт `SERVER_PORT=8080` — это то,
> что используется при локальном запуске через `bootRun`. А `docker-compose.yml`
> задаёт `SERVER_PORT=8090`, потому что порт 8080 на сервере уже занят. Порт
> AudioSocket `8091` в обоих случаях один и тот же.
>
> Поэтому в примерах `curl` ниже указан **8080** — так сейчас запущено. Если
> бэкенд поднят в Docker, подставьте **8090**. Запутаться легко: ошибка будет
> выглядеть как «бэкенд не отвечает», хотя он отвечает на другом порту.

> Если напарник поднимает Asterisk в другой сети — вместо прямого адреса можно
> использовать SSH-туннель:
> `ssh -N -L 8091:127.0.0.1:8091 <user>@10.2.171.217`, и тогда в dialplan писать
> `AudioSocket(127.0.0.1:8091)`.

## 2. Минимальный dialplan

В `extensions.conf` (FreePBX — через веб-интерфейс):

```asterisk
[clinic-inbound]
exten => 100,1,Answer()
  same => n,AudioSocket(10.2.171.217:8091)
  same => n,Hangup()
```

В контексте `from-trunk` или `from-pstn` переадресуйте входящий звонок на `100`.

**Что со стороны Asterisk менять для синтеза речи: ничего.** Сервер отвечает тем же
сокетом, тем же форматом аудио — приложение `AudioSocket()` уже всё умеет.

**Проверить, что до нас доходит связь:**

```bash
# вместо Asterisk может быть любой TCP-клиент — например nc
nc 10.2.171.217 8091
```

Соединение установилось — сеть в порядке. Если `refused`, дальше смотреть не
Asterisk, а бэкенд: запущен ли он, слушает ли 8091.

## 3. Что произойдёт при звонке

1. Asterisk подключается на `8091` и сразу шлёт кадр UUID.
2. Сервер пишет в лог `Звонок #N подключён`.
3. **Сервер голосом говорит** «Для записи на приём сообщите следующую
   информацию: специальность или симптомы, желаемую дату и время.»
4. Пока ассистент говорит, Asterisk продолжает слать аудио — сервер его принимает
   и распознаёт. То, что звонящий сказал поверх приветствия, **не теряется**.
5. Сервер копит речь, ловит паузу ≥1.2 с и распознаёт фразу.
6. Распознанный текст появляется:
   * в логе сервера — `Звонок #N РАСПОЗНАНО: «...»`
   * по HTTP — `GET /api/stt/last`
7. На **первую** распознанную фразу сервер отвечает голосом «Спасибо, записываю»,
   дожидается окончания озвучки и закрывает соединение — Asterisk кладёт трубку.

**Что изменить на стороне Asterisk: ничего.** Ответ уходит теми же кадрами
аудио в тот же сокет, в том же формате (PCM 16 bit, 8 кГц, моно).

> **Про Nagle.** `TCP_NODELAY` обязателен, иначе Asterisk разобьёт кадры на
> неудобные пакеты и в начале речи будут щелчки. Сервер выставляет его сам.

> **Если голоса нет.** Проверьте `GET /api/stt/public/status` → `"ttsReady": true`.
> Если `false`, модель Piper не загрузилась: звонки и распознавание работают,
> но звонящий слышит тишину.

## 4. Как забрать распознанный текст

### Вариант А — без авторизации (для отладки, рекомендуется)

Открытые эндпоинты, **только чтение**, токен не нужен:

```bash
curl -s http://10.2.171.217:8080/api/stt/public/status   # готов ли сервер
curl -s http://10.2.171.217:8080/api/stt/public/last     # последняя фраза
curl -s http://10.2.171.217:8080/api/stt/public/recent   # все фразы
```

Пример ответа:

```json
{
  "found": true,
  "callId": "00010203-0405-0607-0809-0a0b0c0d0e0f",
  "text": "запишите меня к стоматологу завтра",
  "seconds": 3.2,
  "at": "2026-10-13T17:00:00"
}
```

> ⚠️ Там лежат транскрипты разговоров с пациентами. Это осознанная уступка на этапе
> стенда. Перед выкладкой наружу выключается одним флагом: `STT_PUBLIC_READ=false`.
> Основной `/api/stt/*` при этом остаётся под JWT.

### Вариант Б — с авторизацией

```bash
TOKEN=$(curl -s -X POST http://10.2.171.217:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"login":"admin","password":"admin123"}' | jq -r .token)

curl -s http://10.2.171.217:8080/api/stt/last    -H "Authorization: Bearer $TOKEN" | jq
curl -s http://10.2.171.217:8080/api/stt/recent  -H "Authorization: Bearer $TOKEN" | jq
curl -s http://10.2.171.217:8080/api/stt/status  -H "Authorization: Bearer $TOKEN" | jq
```

## 5. Проверка БЕЗ Asterisk — четыре способа

### 5.1. Говорить в микрофон своей машины

Самый быстрый способ убедиться, что всё живо. Asterisk не нужен — скрипт
снимает микрофон и сам делает вид звонка:

```bash
# на машине с бэкендом
python3 deploy/mic-probe.py
```

Говорите, и распознанный текст будет появляться прямо в терминале.
`Ctrl+C` — закончить звонок.

Нужны только `arecord` (пакет `alsa-utils`, обычно уже есть) и `python3`.

### 5.2. С другого компьютера через сеть

Тот же скрипт, но с адресом сервера. Это и есть проверка «связь по сети»,
которую потом повторит напарник со своим Asterisk:

```bash
# на ЛЮБОМ компьютере в той же сети (нужен python3 + arecord)
python3 deploy/mic-probe.py --host 10.2.171.217
```

Что проверяет: TCP до 8091, приём кадров, ресемплинг, распознавание, выдачу
текста. По сути весь путь, кроме самого Asterisk.

Если компьютеры в разных сетях — используйте SSH-туннель вместо прямого
подключения:

```bash
# на своём компе
ssh -N -L 8091:127.0.0.1:8091 -L 8080:127.0.0.1:8080 user@10.2.171.217
# затем на этом же компе
python3 deploy/mic-probe.py --host 127.0.0.1
```

### 5.3. Полный диалог: голос в трубку + распознавание

`mic-probe` только слушает. А `dialog-probe` играет роль Asterisk целиком: подключается,
принимает голос сервера **и одновременно** передаёт ему речь из микрофона:

```bash
# на ЛЮБОМ компьютере в той же сети
python3 deploy/dialog-probe.py --host 10.2.171.217
```

Что должно произойти:

1. вы подключаетесь и **слышите** «Для записи на приём сообщите…»;
2. говорите в микрофон — сервер печатает `ВЫ СКАЗАЛИ (13:41): …`;
3. после паузы ~1.2 с слышите «Спасибо, записываю», соединение закрывается.

#### Если звука нет

На ноутбуках звуком обычно управляет PulseAudio или PipeWire, и прямой доступ к
ALSA-устройству закрыт — `aplay` падает с `Device or resource busy`. Скрипт это
учитывает: пробует `paplay`, потом `ffplay`, потом `aplay -D pulse`, потом прямой
`aplay`, и если ни один не сработал — пишет предупреждение и продолжает без звука.
Голос сервера в любом случае сохраняется в WAV, проверка не срывается.

Что делать, если голоса так и нет:

```bash
python3 deploy/dialog-probe.py --host 10.2.171.217 --player paplay   # задать вручную
python3 deploy/dialog-probe.py --host 10.2.171.217 --no-play         # только WAV
aplay -l                                                               # что вообще есть
```

#### Полезные флаги

| Флаг | Зачем |
|---|---|
| `--file запись.wav` | отдать серверу WAV вместо микрофона (проверка без звука) |
| `--no-play` | не проигрывать голос сервера, только сохранить в WAV |
| `--player paplay\|ffplay\|aplay` | задать проигрыватель вручную |
| `--list-devices` | показать микрофоны (`arecord -l`) и выйти |
| `--max-seconds 180` | предел длительности, чтобы не висеть при молчании |
| `--wav файл` | куда сохранять голос сервера (по умолчанию `reply.wav`) |

Скрипт показывает **только те фразы, что распознаны при этом звонке**: перед
подключением он снимает содержимое хранилища и не выдаёт старые записи за ваши.
Рядом с текстом печатается время — сразу видно, свежая фраза или нет.

### 5.4. Прогон готовой записи

На сервере есть скрипт, который делает вид звонка из WAV-файла. Удобно, чтобы
отделить проблему телефонии от проблемы распознавания:

```bash
./deploy/audiosocket-probe.py --host 10.2.171.217 --port 8091 /путь/к/записи.wav
```

Отдельно убедиться, что сама модель жива вообще без сокета и бэкенда:

```bash
./deploy/stt-smoke-test.sh
```

### Что означают результаты

| Результат | Что это значит |
|---|---|
| `dialog-probe`: слышно приветствие и «Спасибо» | Полный голосовой контур работает, можно звать напарника |
| Голоса нет, в `status` `"ttsReady": false` | Не загрузилась модель Piper — `./deploy/fetch-tts-model.sh`, затем перезапуск |
| Голос есть, но пищит | Потерян фильтр при понижении 22050→8000 Гц |
| `mic-probe` печатает текст | Вся цепочка работает, можно звать напарника |
| `mic-probe` молчит, в логе `накоплено 0 сэмплов` | Микрофон не даёт сигнала — проверьте устройство и уровень |
| `mic-probe` молчит, в логе `речь не распознана` | Звук идёт, но слишком тихо — крутите `STT_SILENCE_RMS_THRESHOLD` |
| `соединение отказано` / таймаут | Не открыт порт 8091 или бэкенд не запущен |
| `Connection refused` на статус-эндпоинте | Бэкенд не поднялся — смотрите лог |

## 6. Протокол AudioSocket — если будете писать клиента сами

Кадры — TLV: `type: uint8`, `length: uint16` (**big endian**), `payload`.

| type | Значение | payload |
|---|---|---|
| `0x00` | Terminate | пусто |
| `0x01` | UUID | 16 байт, шлётся сразу после коннекта |
| `0x10` | Audio | PCM int16, 8 кГц, моно, **little-endian** |
| `0xFF` | Error | код ошибки |

Две ловушки, на которых это обычно и ломается:

1. **Разная разрядность в одном кадре.** Длина — big endian, аудиосэмплы — little endian.
2. **Nagle.** Обязательно `TCP_NODELAY`, иначе Asterisk рвёт кадры. На стороне сервера это уже учтено.

## 7. Ограничения формата и распознавания

- **Частота фиксирована 8 кГц.** Asterisk не даёт её менять; сервер ресемплит в 16 кГц сам.
  Синтез Piper выдаёт 22050 Гц и понижается до 8 кГц с фильтром внутри.
- **Одна длинная фраза — одно распознавание.** Границы определяются паузами ≥1.2 с (`STT_SILENCE_SECONDS`).
- **Фраза длиннее 20 с** распознаётся принудительно (`STT_MAX_UTTERANCE_SECONDS`).
- **Звонок заканчивается после первой распознанной фразы.** Сценарий стендовый:
  приветствие → «Спасибо, записываю» → сокет закрывается. Логика записи к врачу
  в голосовой контур ещё не подключена.
- **STT на этом этапе не связан с записью к врачу.** Распознанный текст пока просто
  отдаётся по HTTP; передача его в диалог — следующий шаг (по ТЗ там же будет
  обращение к чужому бэку клиники по контракту).

## 8. Известные особенности стенда (прочитать до теста)

Это **не** проблемы Asterisk. Если поведение совпадает с описанным ниже —
искать у себя не нужно, мы это уже знаем.

### Фраза «Спасибо, записываю» может не прозвучать

Звучит так: приветствие слышно, клиент говорит, текст распознаётся и появляется
по HTTP — **но голоса ответа нет**, и трубку кладёт примерно через 2 секунды.

Когда так происходит: если клиент заговорил **после** того, как приветствие
договорило. Если начать говорить **во время** приветствия, всё отработает
нормально — эта разница в порядке событий, и её легко не заметить.

Как проверить, что дело не в связи: смотрите в логе бэкенда. Если после строки
`отвечаем «Спасибо, записываю.»` **нет** строки `Озвучено …` — фраза не была
произнесена вообще, дело у нас. Если `Озвучено` есть — проблема в проигрывании
на стороне клиента.

### Микрофон слышит приветствие (эхо)

С гарнитурой микрофон абонента улавливает голос ассистента из динамика. Сервер
распознаёт **свою же** фразу, считает её ответом клиента и досрочно завершает
звонок. В распознанном тексте это видно сразу — там будет «Для записи на приём
сообщите следующую информацию…».

Как провести тест без этого:

* снять гарнитуру, говорить через внешний микрофон или на громкую связь;
* либо начинать говорить **до** конца приветствия.

Настоящее лечение — `EchoCancelator` на стороне Asterisk. Маскировка на нашей
стороне (не реагировать на фразу, совпадающую с только что произнесённой) в
список доработок не входит.

### Звонок может не завершиться

У сервера стоит таймаут 120 секунд на чтение. Но это таймаут на **одно** чтение —
пока идёт аудио, он никогда не срабатывает. Если абонент молчит, а линия не
закрыта, соединение может висеть долго.

## 9. Настройки на стороне сервера

Всё через переменные окружения, ничего в коде менять не нужно:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `STT_ENABLED` | `true` | `false` — порт не поднимается совсем |
| `STT_PUBLIC_READ` | `true` | открытые эндпоинты без JWT. **Перед выкладкой наружу: `false`** |
| `STT_AUDIOSOCKET_PORT` | `8091` | TCP-порт AudioSocket |
| `STT_MODEL_DIR` | `models/stt/sherpa-onnx-...` | каталог модели |
| `STT_SILENCE_SECONDS` | `1.2` | пауза, завершающая фразу |
| `STT_SILENCE_RMS_THRESHOLD` | `0.012` | чувствительность отсечки тишины |
| `STT_MAX_UTTERANCE_SECONDS` | `20` | принудительное распознавание |
| `STT_NUM_THREADS` | `2` | потоков на распознавание |

Синтез речи (`app.tts.*`):

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `TTS_ENABLED` | `true` | `false` — звонящий слышит тишину, но звонки работают |
| `TTS_MODEL_DIR` | `models/tts/vits-piper-ru_RU-irina-medium-int8` | каталог модели Piper |
| `TTS_SPEED` | `1.0` | темп речи |
| `TTS_GREETING` | «Для записи на приём…» | фраза при подключении |
| `TTS_REPLY_ON_SILENCE` | «Спасибо, записываю.» | ответ на первую фразу клиента |

> В `.env` фразы обязательно в кавычках — в тексте приветствия есть двоеточие,
> без кавычек YAML не разберётся.

Если голос распознаётся плохо — в первую очередь крутить
`STT_SILENCE_RMS_THRESHOLD`: телефонная линия тише, чем студийная запись.
