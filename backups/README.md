# Дамп базы

Данные для стенда и для передачи коллеге. Тестовые.

## Что лежит

| файл | что это |
|---|---|
| `clinic-YYYY-MM-DD.sql` | дамп **только схемы `public`** — таблицы приложения, справочники и данные |

Формат обычный `.sql`, а не бинарный: файл читается глазами, диффится и
заливается через `psql` куда угодно без `pg_restore`.

## Как восстановить

```bash
PGPASSWORD=clinic psql -h 127.0.0.1 -U clinic -d clinic -f backups/clinic-2026-10-16.sql
```

В дампе есть `CREATE SCHEMA public;` — на чистой базе это нормально, на базе,
где схема уже есть, эту строку надо убрать (или предварительно
`DROP SCHEMA public CASCADE`).

## Как снять заново

```bash
PGPASSWORD=clinic pg_dump -h 127.0.0.1 -U clinic -d clinic \
  --schema=public --format=plain --encoding=UTF-8 \
  --no-owner --no-privileges --file=backups/clinic-YYYY-MM-DD.sql
```

Ключевые флаги и зачем они:

- **`--schema=public`** — без него в дамп попадает вся база целиком, включая
  служебные объекты. Именно так в первый дамп попали 20 «больших объектов»
  (`lo_create`), которые не относятся к приложению: в наших таблицах нет ни
  одной колонки типа `oid` или `bytea`. Из-за них дамп нельзя было залить
  в ту же базу — OID'ы уже заняты.
- **`--no-owner --no-privileges`** — иначе в дампе окажутся логины владельцев с
  машин, где он снимался, и залить его на другой сервер не выйдет.

## Осторожно: в дампе есть пароли

Таблица `users` хранит `password` — это хеши. Даже для стенда такой файл не
нужно коммитить и выкладывать публично: по нему можно подобрать пароль к
тестовому аккаунту. Папка `backups/` добавлена в `.gitignore`.

Внутри также 93 сессии `dialogue_sessions`, из них 82 с транскриптом разговора:
ФИО и даты рождения, произнесённые вслух. Для стенда это нормально, но по
регламенту РГ-ТЕЛ-01 (раздел 8) такие стенограммы перед передачей третьим лицам
должны быть обезличены.
